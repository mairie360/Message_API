# ADR 0001: Move the messaging real-time channel from SSE to WebSocket

- Status: **proposed** (MAIR-656), to be accepted by the team in review of the three PRs of MAIR-656.
- Date: 2026-11-20
- Tickets: epic MAIR-655; MAIR-656 (this decision and the contract), MAIR-657 (Message_API), MAIR-658
  (BFF_Message), MAIR-818 (Messages_Web_Service), MAIR-660 (Deploiment), MAIR-661 (ZAP, k6, newman),
  MAIR-662 (SSE removal)
- Contract: [`../realtime-websocket.md`](../realtime-websocket.md)

## Context

The messaging service pushes its notifications over **Server-Sent Events**:

```
browser ──fetch stream──► Messages_Web_Service  /stream  (src/lib/message-stream-proxy.ts, cookie → Bearer)
                            ▼
                          BFF_Message           GET /stream          (chat_id → conversation-<id>)
                            ▼
                          Message_API           GET /api/v1/stream   (sse::state::AppState, Redis relay)
```

- `Message_API` keeps the open streams in `sse::state::AppState` (at most 5 per user, the oldest is evicted),
  fans the `ChatEvent`s of every replica out through the Redis relay (`message-api:sse:chat-events`), checks the
  token again every 30 s and closes on expiry or revocation. Signals carry no content: `NEW_MSG`, `MSG_EDITED`,
  `MSG_DELETED` to the members but the author, `CHAT_READ` (with `unread_count`) to the reader's own streams.
  Clients read the change with `GET /api/v1/{chat_id}/?since=` (MAIR-524).
- `BFF_Message` relays the stream, translates `chat_id` into `conversation-<id>`, drops `message_id` and
  `unread_count`, closes after `MESSAGE_STREAM_MAX_MS` (5 min) and reports an upstream refusal with an
  `event: stream_error` because the head of the response is already sent (MAIR-561).
- `Messages_Web_Service` reads the stream with `fetch` + `ReadableStream` (not `EventSource`), and only polls
  every 2 s (`MESSAGE_REFRESH_INTERVAL_MS`) while the stream is not connected. The epic MAIR-655 and the BFF's
  `CONTRACT.md` describe this differently (no consumer / an `EventSource`): both are outdated.

SSE only goes server → client, is one HTTP response per client held by three hops, and cannot report a refusal
once its head is sent. The epic wants a higher throughput and more simultaneous connections; the gain is **not**
granted by the protocol change alone and is measured by the k6 scenario of MAIR-661 against the SSE one.

Constraints found while reviewing the code and the chart:

1. **Only the fronts are exposed.** The `mairie360-stack` Ingress routes `<front>.<domain>` to the fronts; BFFs
   and APIs are cluster-internal.
2. **The BFF reads no cookie.** The front's proxy (`src/lib/bff-proxy.ts`, `proxyPublishedBffRequest` of
   `@mairie360/lib-components/next`) checks the origin, turns the HttpOnly `accessToken` cookie into
   `Authorization: Bearer`, and renews/rotates the session.
3. **A Next.js route handler cannot accept a WebSocket `Upgrade`.** The front runs the standalone `server.js`
   generated by `next build` (`output: "standalone"`).
4. A browser `WebSocket` cannot set an `Authorization` header and **cannot see the HTTP status** of a refused
   handshake (it only gets an `error` then a `close` with code 1006).

## Options

### Transport

| Option | For | Against |
|---|---|---|
| **Keep SSE** | Works today, end to end, plus polling fallback. | One direction only; a refusal after the head is an in-band `stream_error`; one long HTTP response per hop. |
| **WebSocket** | Bidirectional (pings, explicit close codes), one upgraded TCP connection per hop, a refused handshake is a real HTTP status between servers. | New code on three layers, ingress to check (MAIR-660), browser cannot read handshake statuses. |

### Path from the browser to the BFF

| Option | For | Against |
|---|---|---|
| **A. Node server of the front** (chosen) | BFF stays private; the front keeps owning the cookie and the origin check, like every other route; no ingress route to a BFF. | The front leaves the generated `server.js` for a small custom server (Dockerfile and start command change). |
| B. Ingress route straight to the BFF | Front server untouched. | BFF exposed publicly; the BFF must read the cookie and check `Origin` (exception to rule 2); NetworkPolicy opened from the ingress to a BFF. |
| C. One-time ticket | No cookie read by the BFF. | BFF exposed as in B; a single-use ticket needs a shared store the BFF does not have. |

### Transition

| Option | For | Against |
|---|---|---|
| Direct switch | Less code alive at once. | No rollback during a progressive rollout where replicas of both versions coexist. |
| **Coexistence, then removal** (chosen) | SSE stays the fallback until the WebSocket is validated on dev and staging; rollback = front back to SSE. | Both transports maintained for a sprint. |

## Decision

1. **WebSocket end to end**, with the event contract of the SSE unchanged: same four signal types, no content,
   same recipients, catch-up by `?since=` reads. See [`../realtime-websocket.md`](../realtime-websocket.md).
2. **Option A**: `Messages_Web_Service` runs a small Node server around Next that handles the `Upgrade` of `/ws`
   itself (origin check, cookie → Bearer, cookies stripped) and pipes it to `BFF_Message` `GET /ws`, which opens
   `Message_API` `GET /api/v1/ws` with the same Bearer. Tokens never travel in a URL.
3. **Coexistence**: `GET /api/v1/stream` and BFF `GET /stream` stay untouched and working until the WebSocket is
   validated on dev then staging and the front has switched; MAIR-662 then removes them (`feat!`).
4. **One connection registry for both transports** in `Message_API`: the limit of 5 connections per user counts
   SSE and WebSocket connections together, and the same Redis relay and `event_manager` feed both.
5. The capacity goal is measured, not assumed: MAIR-661's k6 WebSocket scenario reports simultaneous connections
   and frame delivery time next to the SSE scenario; targets are set from real usage.

## Consequences

- `Message_API` adds `actix-ws` and a transport-neutral sender in `sse::state` (the SSE formats `data: …\n\n`, the
  WebSocket sends a text frame); the supervisor (30 s revalidation, expiry timer) is shared. The SSE route keeps
  working unchanged (MAIR-657).
- `BFF_Message` adds a WebSocket server and client (`ws`) on its Express HTTP server; `GET /ws` is declared in its
  OpenAPI contract (statuses 101, 401, 429, 503) with the `MessageRealtimeEvent` frame schema, so the front's
  proxy can allow-list it and the contract tests cover it (MAIR-658).
- `Messages_Web_Service` replaces `node server.js` with its own server, and its client replaces the SSE reader:
  WebSocket first, SSE/polling fallback kept until MAIR-662 (MAIR-818).
- The Ingress needs no new route (the WebSocket uses the front host), but Traefik's `buffering` middleware and the
  timeouts must let a long-lived upgraded connection through (MAIR-660).
- newman cannot open a WebSocket: the TI of MAIR-657/658/661 run a small Node `ws` script from the newman stack.
